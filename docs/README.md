# Documentation site

The source of <https://hella-web3.github.io/wiremock-testcontainers-nodejs/> – a
[Docusaurus](https://docusaurus.io/) site in TypeScript, with an API reference generated by
[TypeDoc](https://typedoc.org/). An npm project of its own: its dependencies and scripts are
independent of the library's (pnpm, repository root) and the examples' (`/examples`).

## Running the docs

**Every docs task is an npm script of this project. Run it from the repository root with
`pnpm docs:<script>`, or from `docs` with `npm run <script>` – same script names, same result.**
From the root, `docs` is installed for you whenever its dependencies are missing or out of date.

Once, in the repository root – the API reference is generated from the library's source, which
needs the library's dependencies:

```bash
pnpm install
```

Then, from the repository root:

```bash
pnpm docs:start          # live preview at http://localhost:3000/wiremock-testcontainers-nodejs/
pnpm docs:check          # everything CI checks, before you push
```

or, equivalently, from `docs`:

```bash
npm ci                   # once, and after the lockfile changes
npm run start
npm run check
```

| Task | From the repository root | From `docs` |
|------|--------------------------|--------------|
| Preview with live reload – also on example edits | `pnpm docs:start` | `npm run start` |
| Build the site into `build/` – fails on any broken link or anchor | `pnpm docs:build` | `npm run build` |
| Serve the built site | `pnpm docs:serve` | `npm run serve` |
| Generate the API reference into `docs/api/` (part of `start` and `build`) | `pnpm docs:api` | `npm run api` |
| Type-check | `pnpm docs:typecheck` | `npm run typecheck` |
| Lint | `pnpm docs:lint` | `npm run lint` |
| Unit tests and sync checks, with coverage | `pnpm docs:test:unit` | `npm run test:unit` |
| Build the site, then check every page, snippet and docs link | `pnpm docs:test:e2e` | `npm run test:e2e` |
| **All of the above – the docs' quality gate** | **`pnpm docs:check`** | **`npm run check`** |
| Refresh the snippet copies in the root README | `pnpm docs:sync:markdown` | `npm run sync:markdown` |
| Check them only | `pnpm docs:sync:markdown --check` | `npm run sync:markdown -- --check` |
| Freeze the current docs as a version – before a breaking release | `pnpm docs:version:cut` | `npm run version:cut` |
| Regenerate the API reference even if its inputs are unchanged | `pnpm docs:api --force` | `npm run api -- --force` |

Needs Node.js ≥ 22.18 – the tooling in `src/lib` and `scripts/` is TypeScript that Node.js runs
directly – and a root test keeps the two columns in step: every script in `docs/package.json` has
its `pnpm docs:` twin in the root `package.json`.

### Fast feedback

Measured on a 4-CPU sandbox: from a fresh clone, `pnpm docs:start` serves the site in about 40 s –
24 s of which is the one-time `npm ci`; afterwards it starts in under 10 s, and `pnpm docs:check`
runs the whole gate, build included, in under a minute.

- **Rspack, SWC and LightningCSS** ([Docusaurus Faster](https://docusaurus.io/docs/api/docusaurus-config#future),
  via `future: { v4: true }`) bundle, minify and render the site, with a persistent cache in
  `node_modules/.cache` – a repeated build takes seconds.
- **The API reference is regenerated only when its inputs change** – the library's source, the
  TypeDoc configuration or TypeDoc itself, fingerprinted in `docs/api/.inputs`.
- **The dev server rebuilds only the pages an edit affects.** Editing an example rebuilds the pages
  embedding it; after editing JSDoc in `/src`, run `pnpm docs:api` and the running server picks up
  the new API pages.
- **Tests share their workers**, so TypeScript and the MDX toolchain load once, and the API checks
  parse TypeScript's own declaration files once.

Slow again? Clear the caches with `rm -rf node_modules/.cache .docusaurus docs/api` in `docs`.

## Layout

| Path | Content |
|------|---------|
| `docs` | The pages: `intro`, `getting-started/`, `guides/`, `extensions/`, `reference/`, `contributing/`; `_partials/` are imported by pages |
| `docs/api/` | Generated by TypeDoc – never edit |
| `src/pages`, `src/css/` | The home page and the theme |
| `src/lib` | The tooling: snippet extraction, the remark plugins, the TypeDoc plugin, the API analysis, versioning |
| `scripts` | `api.mts`, `sync-markdown.mts`, `cut-version.mts` – run by Node.js directly |
| `test/unit`, `test/e2e/` | Unit tests and sync checks; the built-site E2E test |
| `typedoc.json` | The API reference: strict validation, source links, descriptions |

## Writing pages

Code never goes into a page. Put it in `/examples` – where it is type-checked, linted and
tested – mark a region, and embed it with an empty code block:

````md
```ts file=stubs/stubs.ts#registrations
```
````

`file=` takes a path below `examples/` and an optional `#region`; the block is titled with the file
and followed by a link to its lines on GitHub. The example file names its page in a header
comment – `@see https://hella-web3.github.io/wiremock-testcontainers-nodejs/docs/guides/registering-stubs`.
Shell commands (`bash`) may be written inline.

Link to other pages by file (`../guides/file-sources.mdx#paths-and-file-urls`); absolute links to
the docs – as JSDoc `@see` tags write them – are turned into site links, so Docusaurus checks
them too.

## What the tests check

- Every snippet reference resolves; every region of the examples is shown; pages contain no
  hand-written TypeScript, JavaScript or JSON; links to repository files point to existing files.
- Every example file links with `@see` to a page showing its folder; every example module is shown.
- Every export and public class member of the library is used in an example (resolved with the
  TypeScript compiler), written in a guide, and listed in `reference/api-overview.mdx`.
- Every JSDoc `@example` in `/src` is an excerpt of an example; every JSDoc `@see` names a page.
- The root README's snippets are in sync.
- Previous major versions are kept, and frozen.
- The built site serves every page of its sitemap; every snippet links to the right lines; every
  docs URL used anywhere in the repository resolves, anchors included.

## Versions

The docs are versioned by the library's **major version** and published from `main`. The current
docs document the major in `package.json`; earlier majors are frozen copies in `versioned_docs/`.
`package.json`'s version decides what the site shows:

| `package.json` | `/docs` | Also on the site |
|----------------|---------|------------------|
| `0.4.1` | `0.x`, the current docs | – |
| `1.0.0-next.2` – the next major, in development | `0.x`, the frozen copy | `/docs/next`: `1.x (next)`, the current docs, with an "unreleased" banner |
| `1.0.0` | `1.x`, the current docs | `/docs/0.x`: the frozen `0.x` docs |

The first breaking change of a major opens it – before it touches the current docs:

```bash
pnpm docs:version:cut                                   # in docs/: npm run version:cut
npm version premajor --preid next --no-git-tag-version  # 0.4.1 → 1.0.0-next.0
```

`version:cut` snapshots the docs and API reference as `versioned_docs/version-0.x`, **freezes**
them – inlining every snippet and pinning source links to the release tag, `v0.4.1`, since `main`
moves on – and adds the version to the version menu. Releasing the major (`pnpm version major`)
then makes its docs the default. A test fails when only one of the two steps was done, naming the
missing command. The whole procedure: [release.md → Major releases](/release.md#major-releases).

`pnpm docs:version:cut 0.x --ref v0.4.1` names label and tag explicitly – required while
`package.json` is a pre-release. `docusaurus.config.ts` derives the version settings from
`package.json` and `versions.json` (`docsVersions()` in `src/lib/versions.mts`): releasing needs no
change to the docs project.

## Dependencies

`package.json` pins some transitive dependencies with `overrides`: `@swc/core`, `@swc/html`,
`vite`, `rolldown` and `@docsearch/react`. Each pinned version satisfies its dependents' ranges;
they were chosen so that `package-lock.json` lists the native binaries of every platform – macOS,
Windows and Linux – which the registry this lockfile was generated against did not provide for
the latest releases. When updating them, check that the lockfile still lists every platform's
`@swc/core-*`, `@rspack/binding-*`, `@rolldown/binding-*` and `@oxlint/binding-*` package.

## Deployment

`.github/workflows/docs.yml` runs `npm run check` – which builds the site – and deploys `build/`
to GitHub Pages on every change to `docs`, `examples/` or `src/` on `main`. Pull requests run the
same checks in `main.yml`.
